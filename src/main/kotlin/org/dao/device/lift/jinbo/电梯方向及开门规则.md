# 电梯方向及开门规则

## 一、核心状态定义

### 1. `JinBoRuntime.direction`

表示电梯的运行方向：

- `Up`
- `Down`
- `Idle`

规则：

- `direction` 一旦确定，电梯优先沿这个方向运行。
- 当前方向没有可继续处理的楼层请求后，才重新决策方向。

### 2. `JinBoRuntime.status` / `liftStatus`

表示电梯当前状态：

- 电梯正在向上移动，高度正在增加：`Up`
- 电梯正在向下移动，高度正在减少：`Down`
- 电梯停在楼层：
  - 开门中
  - 门打开保持
  - 关门中
  - 静止等待
- 统一为：`Idle`

---

## 二、direction 计算规则

### 1. `direction == Idle` 时

根据当前请求队列的物理楼层位置，选择一个初始方向：

- 如果只有当前楼层上方的请求：`direction = Up`
- 如果只有当前楼层下方的请求：`direction = Down`
- 如果上下都有请求：
  - 当前实现规则：先选择距离当前楼层更近的一侧。
- 如果没有任何非当前楼层请求：`direction = Idle`

### 2. `direction == Up` 时

按物理楼层方向判断：

- 如果当前楼层上方还有任何请求：继续 `Up`
- 如果上方没有请求：
  - 下方有请求：改为 `Down`
  - 下方也没有请求：改为 `Idle`

### 3. `direction == Down` 时

- 如果当前楼层下方还有任何请求：继续 `Down`
- 如果下方没有请求：
  - 上方有请求：改为 `Up`
  - 上方也没有请求：改为 `Idle`

### 4. 顶层 / 底层外部请求特例

#### 顶层特例

- 顶层只有 `Down` 外部请求。
- 电梯可以先以 `Up` 方向到达顶层。
- 到达顶层后，根据 `arrivalMatches` 服务这个 `Down` 请求。
- 开门处理完当前方向请求后，`Up` 方向没有后续请求，再切换成 `Down`。

#### 底层特例

- 底层只有 `Up` 外部请求。
- 电梯可以先以 `Down` 方向到达底层。
- 到达底层后，根据 `arrivalMatches` 服务这个 `Up` 请求。
- 开门处理完后，`Down` 方向没有后续请求，再切换成 `Up`。

---

## 三、移动规则

### 1. 允许移动的条件

只有同时满足：

- `direction != Idle`
- `status` 处于移动方向
- 所有门都已经 `CLOSE`

才允许改变电梯高度。

### 2. 移动过程

电梯沿当前方向逐层推进。

每经过一层：

1. 先检查当前楼层是否有“当前方向可服务”的请求。
2. 有：
   - 停止移动
   - `status = Idle`
   - 打开对应门
3. 没有：
   - 继续沿当前方向前进
   - 按 direction 规则检查是否继续当前方向

### 3. 移动中收到新请求

如果新请求的目标楼层是“当前楼层”：

- 只有电梯高度精确等于该楼层高度时，才允许立即处理该请求。
- 高度不一致时：
  - 请求先正常入队
  - 不立即开关门
  - 电梯继续处理原本的任务
  - 等高度同步到该楼层后，再由正常过程处理

如果新请求在其他楼层：

- 入队。
- 如果它在当前方向的前方，后续可能优先处理。
- 如果它在反方向，不打断当前方向；等当前方向没有后续请求后再处理。

---

## 四、到站开门规则

### 1. 到站判断

当 `status == Up / Down` 且电梯高度推进到某楼层高度时，视为到达该楼层。

### 2. 开门判断

在当前楼层，只有满足下面条件的请求，才决定开门：

- `req.destFloor == currentFloor`
- 请求方向与当前电梯运行方向匹配：
  - 梯内请求：不看方向
  - TCP 请求：不看方向
  - 梯外 `Up` 请求：要求到达方向为 `Up`，或底层特例
  - 梯外 `Down` 请求：要求到达方向为 `Down`，或顶层特例

### 3. 多请求同层

同一楼层同时有多个请求：

- 只打开匹配当前方向的请求对应的门。
- 只清理匹配当前方向的请求。
- 其他方向请求保留，等方向切换后再服务。

---

## 五、清理请求规则

门已经打开后，清理满足以下全部条件的请求：

1. `req.destFloor == currentFloor`
2. 请求匹配到站时的方向：
   - 使用 `JinBoDirection.arrivalMatches`
   - 梯外顶层/底层特例保留
3. 请求要求打开的门已经全部为 `OPEN`

不符合的请求不能被清理。

---

## 六、同层请求刷新自动关门时间规则

当收到一个当前楼层请求时：

必须先满足：

- `req.destFloor == currentFloor`
- 电梯高度与该楼层高度一致
- 请求匹配当前 direction

然后：

- 梯内 / TCP 请求：
  - 可以刷新对应门的自动关门时间
- 梯外请求：
  - 必须请求方向与当前 `direction` 一致，才刷新自动关门时间

---

## 七、门的规则

### 门状态

- `OPENING`
- `OPEN`
- `CLOSING`
- `CLOSE`
- `ERROR`

### 允许开门

只有：

- `status == Idle`
- 非急停
- 不在移动中

才允许开始开门。

### 允许关门

- 关门指令不区分门。
- 不修改 direction。
- 只触发门从 `OPEN/OPENING` 进入 `CLOSING`。

### 移动前必须门全关

必须所有门都是 `CLOSE`，电梯才可以移动。

---

## 八、急停规则

### 进入急停

- 禁止移动。
- 禁止开门。
- 门计时冻结。

### 解除急停

- 不自动移动。
- 由请求队列重新计算 direction。
- 再决定是否开始运行。

---

## 九、请求入口规则

### HTTP / TCP / 页面按钮

统一进入 `JinBoCommandService.request`。

### 回放模式

- 页面按钮呼梯、开门、关门：禁止。
- TCP / HTTP 呼梯：仍然允许。

### 无效 doorCodes

- 如果请求包含不存在的门号，整个请求不接收。

### 去重

- 相同请求已在队列时，不重复入队。

---

## 十、状态与方向一致性

- 没有请求时：
  - `status = Idle`
  - `direction = Idle`
- 移动中：
  - `status` 和 `direction` 保持一致，例如：
    - `direction == Up`
    - `status == Up`
- 停车开门/关门：
  - `status == Idle`
  - `direction` 保留为到站时的方向，用于后续方向决策和清理请求。
